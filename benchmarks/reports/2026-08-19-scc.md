# SCC benchmark report

This report supersedes the preliminary 2026-08-17 SCC report, which measured a dirty
working tree on a different machine. Its absolute numbers are not comparable to these.

## Configuration

The benchmark ran on 2026-08-19 on an Apple M4 Mac mini with four performance cores, six efficiency cores, and 16 GB of memory.

The operating system was macOS 15.6 (build 24G84), Darwin 24.6.0, on `arm64`.

The compiler was `rustc 1.95.0 (59807616e 2026-04-14)`.

The build used the workspace release profile, including LTO and one codegen unit.

The binary installs mimalloc as the global allocator. This workload is allocation-bound, so a reproduction under the system allocator will not match.

The revision was `1d02e4d515cf629d2f685134ddf5b5221f278c9b` with a clean working tree, and every record in this report carries `"dirty": false`.

Each point used one timely worker, seed `3237998146`, two warmup runs, and eight measured runs.

Eight runs is two complete rotations of the four implementations, so each implementation leads a repetition exactly twice.

Each graph contained twice as many generated edges as nodes.

Both compiled implementations used the node identifier to select the same logarithmic label-introduction round as DDIR's `enter_at($1[0])`.

The reported times are medians of `measured_ns` across the eight runs.

The [raw JSONL records](2026-08-19-scc.jsonl) contain all 96 measured implementation runs.

## Ratios

| Nodes | Plan / optimized | Vec / plan | Corgi / Vec | Corgi / plan |
| ---: | ---: | ---: | ---: | ---: |
| 1,000 | 1.047x | 3.227x | 0.904x | 2.918x |
| 10,000 | 1.073x | 3.473x | 0.857x | 2.978x |
| 100,000 | 1.079x | 4.026x | 0.762x | 3.067x |

The typed DDIR plan is 4.7% slower than optimized typed SCC at 1,000 nodes and 7.9% slower at 100,000 nodes.

This is the cost visible from using DDIR's generic operator plan instead of the specialized typed implementation.

Vec interpretation takes between 3.2 and 4.0 times the typed DDIR plan's time, with the ratio increasing across these three sizes.

Corgi improves relative to Vec as the graph grows, from 0.904x of Vec time at 1,000 nodes to 0.762x at 100,000 nodes.

Corgi remains between 2.9 and 3.1 times the typed DDIR plan at all three sizes.

## What this benchmark does not separate

The operator scorecard splits its compiled implementation in two, so that DDIR's runtime embedding — rendering inside an iterative scope at `Product<u64, PointStamp<u64>>` — is charged separately from interpretation.

SCC does not make that split. Both of its compiled implementations already render in nested iterative scopes, at `Product<_, usize>` rather than at `PointStamp`. `Plan / optimized` here means what it always meant: the cost of DDIR's operator plan against a specialized one. It does not isolate the timestamp.

So the `Vec / plan` column for SCC still contains whatever the `PointStamp` lattice costs relative to `Product<_, usize>`, while the operator scorecard's `Vec / embedded` column does not. The two benchmarks' interpretation ratios are therefore not directly comparable, and a `compiled-ddir` variant rendered at DDIR's own timestamp is the obvious next step for this workload.

## Correctness and variation

All four implementations produced identical consolidated weighted outputs at every scale, with matching digests: `35248ebae1c95da1` at 1,000 nodes, `f68c8364290a7385` at 10,000, and `b0b28b0bcb6107ea` at 100,000.

Max-minus-min as a percentage of the median, over the eight measured runs:

| Nodes | Compiled | Compiled DDIR plan | DDIR Vec | DDIR Corgi |
| ---: | ---: | ---: | ---: | ---: |
| 1,000 | 3.71% | 2.21% | 2.99% | 3.51% |
| 10,000 | 1.49% | 2.10% | 2.84% | 1.55% |
| 100,000 | 0.77% | 0.60% | 1.49% | 1.25% |

Dispersion is under 4% everywhere and falls with size, so all three size points support the ratios quoted above.

Stabilization accounted for at least 99.0% of measured time in every run.

This workload therefore says little about parsing, lowering, dataflow construction, or ingestion costs. The operator scorecard is where those are visible.

## Limits

The sweep used one seed, one edge density, one worker, and one input batch.

SCC structure depends on the graph generator, so these results should not be generalized to other graph families.

The timed stabilization phase includes capture of the full result, which the operator scorecard excludes. For Corgi that capture includes converting the output back into rows, so Corgi's SCC number carries a cost its operator-scorecard numbers do not.

Correctness is checked against `compiled-ddir`, which is in turn cross-checked by the independent `strongly_connected_at` implementation. The `checked_against` field records this.
